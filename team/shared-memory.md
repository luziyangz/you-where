# Shared Memory

## 项目事实
- 项目类型：原生微信小程序 + Python FastAPI 后端
- 小程序主入口：`app.js`、`app.json`
- 后端主入口：`backend/app_main.py`
- 当前后端主 API 版本：`/api/v2`
- 当前数据层：SQLAlchemy；配置显示默认支持 MySQL，也兼容 SQLite 本地模式

## 当前业务主线
- 登录
- 绑定共读伙伴
- 创建共读书籍
- 记录阅读进度 / 笔记
- 查看进度与回复
- 查看个人信息、阅读历史、阅读目标、提醒配置
- 书城搜索、详情、分页阅读

## 已识别的结构问题
- `backend/service`、`backend/repo` 目录存在但尚未承接真实业务逻辑
- 部分中文文档与注释存在编码混乱
- 存在疑似模板残留页面：`pages/index`、`pages/logs`
- 存在历史归档目录：`archive/2026-03-26`
- 仓库中有疑似不应保留在主仓库根主线内的二进制文件：`backend/docker-compose-linux-x86_64`

## 当前治理策略
- 第一阶段只做“低风险、可验证”的治理：
  - 建立协作机制
  - 清理明显无引用残留
  - 建立计划与记录制度
  - 运行现有后端测试验证主链路
- 第二阶段再进入结构重构与能力增强：
  - 前后端契约梳理
  - 分层重整
  - 稳定性与并发治理
  - 自动化测试补强

## 2026-04-27 产品方向结论
- 产品定位调整为“情侣/朋友双人共读陪伴小程序”。
- 当前只支持 2 人结伴，不进入小组/社区模式。
- 内容方向强调心学、术数、中医经络、国学、历史与传统文化，少量保留适合双人共读的国外名著。
- 首页需要强调伙伴关系和当前共读状态，而不是普通工具入口。
- 商业化未来会考虑，但当前阶段先打磨产品闭环和体验。
- 已新增 `team/PRD.md` 作为 PRD v0.1。

## 2026-04-27 产品讨论第 4 轮结论
- 书城定位为“适合两个人一起读的主题书房”，不做普通全部书籍列表。
- 分类升级为心性共修、国学经典、术数入门、经络养生、历史人物、双人共读。
- 书籍卡片需要突出共读理由、适合关系和阅读节奏。
- MVP 阶段每个分类 3-6 本精选书，总量控制在 20-30 本。
- 详情页需要回答“为什么适合我们一起读”。

## 2026-04-27 产品讨论第 5 轮结论
- 阅读/进度页定位为“我们这本书读到哪里了，TA 最近留下了什么”。
- 第一屏优先展示当前书、双方进度对比、下一步行动和 TA 最新动态。
- 进度展示要有陪伴感，不做强竞争。
- 笔记流应像双人共读日记，不像公开评论区。
- 回复保持单层轻互动。
- 双方完读后需要小仪式感，展示共读天数、笔记数量，并引导归档或选下一本。

## 2026-04-27 产品讨论第 6 轮结论
- 我的页定位为“个人资料与共读资产管理”，不是第二个首页。
- 信息优先级为个人资料、共读资产、阅读目标、阅读历史、提醒设置、设置/协议/关于。
- 阅读目标是轻坚持方向，不是 KPI。
- 阅读历史是双人记忆，不是普通列表。
- 提醒是温柔提醒，不做强打卡压迫。
- 当前阶段不放复杂会员入口、强运营 Banner 或测试用户入口。

## 2026-04-27 产品/UI 工作约束更新
- 产品讨论不再硬卡 15 轮，改为 18-24 轮内收束，最迟第 24 轮完成定稿。
- 设计必须避免明显 AI 味：模板化卡片堆叠、空泛渐变、无差异文案、装饰大于信息、功能堆砌。
- UI 决策必须围绕情侣/朋友双人关系、特色内容气质、当前状态和下一步行动。
- 如需要外部 skill，可以在线加载；优先选择安装量高、来源可信、与当前任务直接相关的技能。

## 2026-04-27 产品讨论第 7 轮结论
- 登录前不能只是“请登录”，需要先解释双人共读价值。
- 推荐登录前主文案为“和重要的人，一起读完一本书”。
- 登录前可展示轻量预览：双人进度、特色书房、共读关系文案。
- 登录前不展示真实完整书城、业务 tab、测试用户入口、共读码/二维码和商业化 Banner。
- 新用户引导采用状态驱动，不做长教程。

## 2026-04-27 产品讨论第 8 轮结论
- 品牌语气确定为：温柔、克制、有陪伴感，带一点东方气质，但不故作玄虚。
- 文案要避免 AI 味、强打卡压迫感、过度玄学和普通工具味。
- 文案多使用“我们、一起、慢慢、留下、回应”等关系型表达。
- 产品名可保留“你在哪里”，副标题建议为“和重要的人一起共读”或“一本书，两个人慢慢读”。
- 后续页面文案必须检查是否像真人说话、是否服务当前状态、是否有双人关系感、是否避免压力和玄虚。

## 2026-04-27 产品讨论第 9 轮结论
- UI 视觉方向确定为“温润纸感 + 东方书房 + 双人关系”。
- 不做通用绿白工具小程序，也不做厚重玄学风。
- 色彩系统建议：纸米色、松烟墨、青瓷绿、朱砂红、暖灰。
- 字体策略以小程序兼容为前提，通过字号、字重、字距和数字样式建立气质。
- 组件强调轻纸张卡片、弱阴影、单主 CTA、低权重危险操作、减少无意义图标。
- 反 AI 味检查：避免卡片堆叠、无意义渐变、按钮同权重、泛化文案、缺少关系感和内容气质。

## 2026-04-27 产品讨论第 10 轮结论
- 核心状态统一为：未登录、已登录未绑定、已绑定无书、已绑定有书未记录、已绑定有书有动态、双方完读、异常/失败。
- 产品体验由状态驱动，而不是功能入口驱动。
- 每个状态只保留一个主行动。
- 空状态必须告诉用户下一步。
- 首页、结伴页、书城页、进度页、我的页共享同一套状态口径。
- 后续 UI 和文案不使用通用“暂无数据”。

## 2026-04-27 产品讨论第 11 轮结论
- UI 改版不能只验收功能可点，必须同时验收状态、主 CTA、文案、双人关系感、异常下一步和反 AI 味。
- 测试分为自动化回归、人工状态验收、真机验收三层。
- 产品验收红线包括：“暂无数据”主空态、多个同权重主按钮、绑定后大面积二维码、首页功能九宫格、默认展示不可加入书籍、AI 模板文案、异常只显示接口错误。
- 每次 UI 改版必须附带状态变更、主 CTA、空/异常文案、自动化验证和人工验收结果。

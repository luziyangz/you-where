# 产品需求文档 PRD

## 版本信息
- 产品名称：你在哪里 / 双人共读陪伴小程序
- PRD 版本：v0.1
- 当前阶段：本地开发与云端联调阶段
- 更新时间：2026-04-27

## 一、产品定位

本产品定位为“情侣/朋友之间的双人共读陪伴小程序”。

产品核心不是泛书城，也不是单人的阅读记录工具，而是围绕一个固定伙伴建立轻量、持续、有反馈的共读关系。用户通过共读码或二维码绑定伙伴后，一起选择一本书，共享进度、记录笔记、互相回复，最终形成双人阅读记忆。

当前内容方向强调差异化，不走纯大众书城路线，重点沉淀以下特色内容：

- 心学
- 术数
- 中医经络
- 国学经典
- 历史与传统文化
- 少量适合双人共读的国外名著

## 二、产品目标

### 短期目标
- 完成“登录 -> 结伴 -> 选书 -> 共读 -> 记录 -> 回复 -> 归档”的最小闭环。
- 让用户第一次进入后能清楚知道自己和伙伴当前处于什么状态。
- 让结伴关系成为产品主视觉和主叙事，而不是隐藏在功能菜单中。
- 让特色书库形成产品识别度，避免变成普通书城。

### 中期目标
- 增强共读仪式感：连续共读天数、共同完成书籍、伙伴回应、阶段性总结。
- 完成提醒真实投递、目标反馈、阅读历史沉淀。
- 形成更明确的内容栏目，例如“心学共修”“术数入门”“经络养生”“国学经典”。

### 长期目标
- 在产品效果被验证后，预留商业化能力。
- 商业化方向暂不进入当前实现范围，但产品结构应避免后续难以扩展。

## 三、目标用户

### 核心用户
- 情侣：希望通过共读建立共同话题和长期陪伴。
- 朋友：希望互相监督、保持阅读习惯。
- 学习搭子：希望围绕传统文化、心学、术数、中医等主题共同学习。

### 用户动机
- 一个人读书容易放弃。
- 读完没有人交流，缺少反馈。
- 想和亲近的人建立共同成长记录。
- 对心学、国学、中医、术数等内容感兴趣，但需要陪伴和路径。

## 四、产品原则

- 双人关系优先：页面设计优先展示“我和伙伴”的关系状态。
- 陪伴优先于效率：不做复杂阅读器，不追求工具感过强。
- 特色内容优先：书城内容要体现心学、术数、中医、国学等差异化。
- 轻量互动：回复、提醒、进度反馈要简单，不做重社区。
- 当前只支持 2 人关系：不引入小组、圈子、排行榜等复杂关系。

## 五、核心用户流程

```text
进入小程序
-> 登录
-> 查看自己是否已有伙伴
-> 复制共读码 / 展示二维码 / 扫码绑定
-> 选择一本特色内容书籍
-> 开始共读
-> 阅读并同步进度
-> 写下笔记
-> 伙伴查看并回复
-> 双方完成后归档
-> 在我的页查看历史、目标、提醒
```

## 六、MVP 功能范围

### 必须完成
- 微信一键登录
- 手机号登录
- 登录后才能使用主功能
- 共读码展示与复制
- 共读二维码展示、预览、保存
- 扫一扫绑定
- 2 人绑定与解绑
- 特色分类书城
- 书籍详情
- 加入共读
- 阅读分页
- 进度同步
- 笔记记录
- 伙伴回复
- 阅读历史
- 阅读目标
- 提醒配置
- 我的资料

### 暂不进入当前版本
- 多人小组
- 排行榜
- 公开社区
- 付费会员
- 付费书单
- 课程售卖
- 复杂勋章体系
- AI 解读内容

## 七、页面需求

### 0. 新用户引导与登录前体验

登录前首页不能只是“请登录”。它需要先解释产品价值，让用户知道这是适合亲近关系的双人共读产品。

登录前第一屏目标：
- 让用户知道这是双人共读。
- 让用户感到这是适合情侣/朋友等亲近关系的产品。
- 让用户愿意登录并邀请一个人。

推荐主文案：
```text
和重要的人，一起读完一本书
```

推荐副文案：
```text
选一本书，记录彼此读到哪里，也留下只属于你们的想法。
```

登录前允许展示轻量预览：
- 双人共读卡片预览：你和 TA 的虚拟进度、TA 的新笔记。
- 特色书房预览：心性共修、国学经典、经络养生等方向。
- 共读关系预览：强调“不是一个人打卡，是两个人慢慢把一本书读完”。

登录前不展示：
- 真实完整书城列表。
- 复杂功能入口。
- 可跳转业务 tab。
- 测试用户入口。
- 共读码或二维码。
- 商业化 Banner。

新用户引导采用状态驱动，不做长教程：
```text
未登录 -> 解释产品价值
已登录未绑定 -> 引导邀请伙伴
已绑定无书 -> 引导选书
已有书无笔记 -> 引导记录第一条进度
```

### 1. 首页

首页应该强调“我和伙伴当前怎么样”，而不是只做功能入口。

未登录状态：
- 展示产品价值：和重要的人一起读完一本书。
- 提供微信登录和手机号登录。
- 不允许直接进入主功能页面。

已登录但未绑定：
- 强调“还没有共读伙伴”。
- 主 CTA：去结伴。
- 次 CTA：了解共读玩法。

已绑定但无在读书：
- 展示伙伴信息。
- 主 CTA：选择一本书开始共读。
- 展示已结伴天数。

已绑定且有在读书：
- 展示当前共读书。
- 展示双方进度。
- 主 CTA：继续阅读 / 记录进度。
- 展示伙伴最近动态。

### 2. 结伴页

职责：
- 展示我的共读码。
- 支持一键复制。
- 展示共读二维码。
- 支持扫码绑定。
- 展示伙伴关系。
- 支持解绑。

体验要求：
- 共读码复制入口只保留一个明确图标。
- 二维码要完整、清晰、可扫码。
- 未绑定时强调邀请对方。
- 已绑定时强调关系状态，而不是继续引导绑定。
- 绑定前和绑定后必须是两套不同的信息架构：
  - 绑定前是工具型页面，核心任务是“邀请/绑定对方”。
  - 绑定后是关系型页面，核心任务是“展示和经营我与 TA 的共读关系”。
- 绑定后默认弱化二维码，不再让二维码占据主视觉；二维码可放入折叠区或弹窗中。
- 绑定后应优先展示头像、昵称、结伴天数、当前共读书、双方进度和下一步行动。

### 3. 书城页

职责：
- 展示特色内容分类。
- 支持搜索。
- 支持进入书籍详情。

核心分类：
- 心性共修：心学、修心、处世、成长
- 国学经典：论语、大学、中庸、道德经等
- 术数入门：塔罗、紫微斗数、易经基础、命理入门
- 经络养生：中医经络、气血、作息、养生
- 历史人物：人物传记、历史故事、王阳明、曾国藩等
- 双人共读：适合情侣/朋友讨论的小说、散文、国外名著

体验要求：
- 中文内容优先。
- 书籍必须可加入共读，不允许展示不可用书籍作为主推荐。
- 分类文案要体现内容气质，不要像普通电商分类。
- 书城不是普通全部书籍列表，而是“适合两个人一起读的主题书房”。
- 默认推荐应优先展示有讨论空间、共同成长感、适合慢读且内容完整的书。
- 不默认展示英文原文、无正文、过度工具化、过于晦涩且无导读、存在合规风险的内容。
- MVP 阶段建议每个分类 3-6 本精选书，总量控制在 20-30 本。

书籍卡片建议字段：
- 书名
- 作者 / 分类
- 一句共读理由
- 适合关系：情侣 / 朋友 / 学习搭子
- 阅读节奏：轻读 / 慢读 / 深读
- 操作按钮：一起读

书籍详情页应补充：
- 内容简介
- 共读理由
- 适合谁一起读
- 预计阅读强度
- 推荐讨论问题
- 开始共读按钮

### 4. 书籍详情页

职责：
- 展示书名、作者、分类、简介。
- 展示适合共读的理由。
- 展示预计阅读页数。
- 支持加入共读。

限制：
- 未绑定伙伴时，引导去结伴。
- 已有在读书时，不允许重复加入新书。
- 无正文内容时，不允许加入共读。

### 5. 阅读/进度页

职责：
- 展示当前书籍。
- 展示双方进度。
- 支持记录进度和笔记。
- 支持查看伙伴笔记。
- 支持回复。

体验要求：
- 强调“我们正在一起读到哪里”。
- 进度不是单人数据，应优先呈现双人对照。
- 笔记流应体现对方参与感。
- 页面定位不是“我的读书记录”，而是“我们这本书读到哪里了，TA 最近留下了什么”。
- 第一屏优先展示双人进度卡片和 TA 的最新动态。
- 全量笔记流可以放在下方，不应默认挤满第一屏。
- 双方进度展示应偏陪伴感，避免制造强竞争感。
- 笔记流应像双人共读日记，而不是公开评论区。
- 回复机制保持轻量，只做单层回复，不做楼中楼。
- 双方完读后需要有小仪式感，展示共读天数、笔记数量，并引导归档或选下一本。

推荐信息优先级：
1. 当前共读书
2. 我和 TA 的阅读进度对比
3. 下一步行动：记录进度 / 继续阅读
4. TA 最近的笔记或回复
5. 全部共读动态流
6. 完读归档入口

### 6. 我的页

职责：
- 展示个人信息。
- 展示阅读目标。
- 展示历史记录。
- 展示提醒配置。
- 展示设置入口。

体验要求：
- 我的页不抢主线，不应比首页更像工作台。
- 目标、历史、提醒是辅助能力。
- 我的页定位为“个人资料与共读资产管理”，不是第二个首页。
- 信息优先级：个人资料、共读资产、阅读目标、阅读历史、提醒设置、设置/协议/关于。
- 阅读目标不应像 KPI，应表达为“给我们一个轻轻坚持的方向”。
- 历史记录应表达为“双人记忆”，而不是普通书籍列表。
- 提醒不应是强打卡，应是温柔提醒。
- 当前阶段不在我的页放复杂会员入口、强运营 Banner 或测试用户入口。

我的页建议结构：
- 顶部：头像、昵称、加入天数
- 资产卡片：共读过几本书、留下几条笔记、累计共读天数
- 目标卡片：本周期目标进度
- 历史入口：看过去一起读过的书
- 提醒入口：设置读书提醒
- 设置入口：协议、隐私、退出登录

## 八、验收标准

### 登录
- 未登录用户点击底部非首页 tab，不应闪屏跳转。
- 登录成功后能恢复用户信息和共读状态。

### 结伴
- 用户能看到自己的 6 位共读码。
- 点击复制图标后，剪贴板写入共读码。
- 二维码完整显示，不裁切。
- 扫描对方二维码后能自动填充并绑定。
- 自己绑定自己时给出明确提示。
- 输入不存在共读码时给出明确提示。

### 书城
- 默认展示中文特色分类。
- 点击分类后列表内容变化。
- 进入详情的书籍可以加入共读。
- 不展示英文不可用书籍作为默认主内容。

### 共读
- 绑定伙伴后才能加入共读书。
- 同一对伙伴同一时间只能有一本在读书。
- 记录进度后双方页面状态能同步。
- 伙伴未读笔记支持标记已读。
- 未解锁笔记不能回复。

### 提醒
- 能保存提醒偏好。
- 未配置真实微信模板时，应明确提示当前只是配置保存。
- 真实投递必须依赖微信模板和服务器调度。

## 九、非功能要求

- 稳定性：核心写操作必须具备幂等或并发兜底。
- 可维护性：后端遵循 router -> service -> repo 分层。
- 状态一致性：前端全局状态统一由 `app.js` 写入口同步。
- 部署：后端支持 Docker Compose 云端部署。
- 测试：关键主链必须有自动化回归。

## 十、商业化预留

当前不实现商业化，但产品结构需要预留：

- 付费特色书单
- 主题共读计划
- 课程或训练营
- 会员权益
- 专家/老师内容
- 私域社群转化

当前版本不讨论价格、支付、会员体系，只确保内容分类、阅读历史、目标和用户关系数据未来可承接商业化。

## 十一、当前风险

- 域名未备案，正式小程序上线受限。
- 微信手机号登录和订阅消息仍需真机验证。
- 二维码扫码和保存相册仍需真机验证。
- 当前 UI 还偏功能堆叠，需要围绕“伙伴关系”重新设计首页和结伴页。
- 内容分类已有方向，但书籍质量和内容运营标准仍需继续打磨。

## 十二、品牌文案语气

品牌语气定位：

```text
温柔、克制、有陪伴感，带一点东方气质，但不故作玄虚。
```

文案应避免：
- AI 味：如“开启高效阅读之旅”“打造知识闭环”。
- 强打卡压迫感：如“你今天还没完成任务”“目标失败”。
- 过度玄学：如“唤醒灵魂频率”“开启命运能量连接”。
- 普通工具味：如“暂无数据”“操作成功”。

文案应多使用：
- 我们
- 一起
- 慢慢
- 留下
- 回应
- 今天读到哪里

关键场景推荐文案：
- 未登录：和重要的人，一起读完一本书
- 未绑定：还差一个共读伙伴
- 绑定成功：你们已成为共读伙伴
- 无在读书：选一本适合你们慢慢聊的书
- 有新笔记：TA 留下了一句话，等你来看
- 记录进度：记录今天读到哪里
- 提醒：今晚要不要和 TA 一起读几页？
- 完读：你们一起读完了这本书
- 空状态：还没有笔记，先留下第一句吧。

页面文案检查标准：
- 是否像真人说的话？
- 是否服务当前状态？
- 是否有双人关系感？
- 是否避免压力和玄虚？
- 是否避免模板化 AI 表达？

产品名称建议保留“你在哪里”，但增加明确副标题：

```text
你在哪里
和重要的人一起共读
```

或：

```text
你在哪里
一本书，两个人慢慢读
```

## 十三、UI 视觉方向

视觉方向定位：

```text
温润纸感 + 东方书房 + 双人关系
```

UI 不做通用绿白工具小程序，也不做厚重玄学风。整体应像一个可以慢慢停留的双人书房：安静、温暖、留白充足，有纸张、墨色、印章、书签、线装书等东方文化的轻提示，但不能堆砌符号。

### 视觉关键词
- 温润
- 克制
- 纸感
- 书房
- 留白
- 关系感
- 慢读
- 轻东方

### 色彩方向

主色不建议继续依赖微信绿作为品牌主色。微信绿可以保留为系统成功态，但产品主色建议采用：

- 纸米色：页面背景，降低冷白感。
- 松烟墨：主要文字和重点标题。
- 青瓷绿：主 CTA 和关系状态。
- 朱砂红：少量用于印章、完成、提醒，不大面积使用。
- 暖灰：分割线、辅助信息。

建议色彩语义：
- 主背景：纸米色 / 暖白
- 主文字：墨色
- 主行动：青瓷绿
- 关系点缀：朱砂红或淡金
- 卡片：白中带暖，不使用纯白硬卡片

### 字体方向

小程序端无法稳定依赖复杂 Web 字体，因此字体策略应务实：

- 标题：使用较大字号、较高字重、适当字距形成气质。
- 正文：保持系统字体，保证可读性。
- 数字：用于共读码、页码、天数时可使用更强字重和更大字号。
- 不强行引入花哨字体，避免加载和兼容问题。

### 组件风格

卡片：
- 圆角适中，不要所有卡片都大圆角。
- 阴影要轻，更多依赖背景层次和边框。
- 关键卡片可使用“纸张浮层”效果。

按钮：
- 主按钮只保留一个，颜色明确。
- 次按钮低饱和，不和主 CTA 抢视觉。
- 危险操作如解绑低权重展示。

图标：
- 图标数量减少，优先服务识别。
- 不使用过多 emoji。
- 复制、扫码、保存等工具图标保持轻量。

状态卡：
- 首页和进度页应重点设计状态卡，而不是功能九宫格。
- 状态卡内容必须回答“我们现在怎么样，下一步做什么”。

### 页面视觉原则

- 首页：像双人共读状态卡，不像功能工作台。
- 结伴页：绑定前工具型，绑定后关系型，两套视觉层级。
- 书城页：像主题书房，不像商品货架。
- 进度页：像双人读书日记，不像评论列表。
- 我的页：像个人共读资产，不像运营中心。

### 反 AI 味检查

每个页面设计前必须检查：
- 是否只是卡片堆叠？
- 是否用了无意义大渐变？
- 是否所有按钮都一样重？
- 是否文案可以替换到任何 App？
- 是否缺少“我和 TA”的关系感？
- 是否缺少内容气质？

如果答案为是，需要重新设计。

## 十四、核心状态设计

产品体验由状态驱动，而不是由功能入口驱动。首页、结伴页、书城页、进度页、我的页必须共享同一套状态口径。

### 状态 1：未登录

用户问题：
```text
这是什么？为什么要登录？
```

页面策略：
- 首页解释产品价值。
- 其他 tab 不切页，提示登录。
- 不展示共读码、二维码、书城完整内容。

主文案：
```text
和重要的人，一起读完一本书
```

主 CTA：
```text
微信一键登录
```

### 状态 2：已登录未绑定

用户问题：
```text
我该邀请谁？
```

页面策略：
- 首页引导去结伴。
- 结伴页强展示共读码、二维码、输入框、扫一扫。
- 书城可以预览，但加入共读时引导先绑定。

主文案：
```text
还差一个共读伙伴
```

主 CTA：
```text
去邀请伙伴
```

### 状态 3：已绑定无书

用户问题：
```text
我们读什么？
```

页面策略：
- 首页展示伙伴关系。
- 结伴页展示关系状态。
- 书城成为主行动入口。
- 进度页引导去选书。

主文案：
```text
选一本适合你们慢慢聊的书
```

主 CTA：
```text
去主题书房
```

### 状态 4：已绑定有书未记录

用户问题：
```text
我该先做什么？
```

页面策略：
- 首页展示当前书和双方空进度。
- 进度页引导记录第一条进度。
- 阅读器引导同步当前页。

主文案：
```text
你们的第一条共读记录，还等着被写下
```

主 CTA：
```text
记录今天读到哪里
```

### 状态 5：已绑定有书有动态

用户问题：
```text
TA 最近读到哪了？TA 留了什么？
```

页面策略：
- 首页展示 TA 最新动态摘要。
- 进度页展示双人进度卡和 TA 最新笔记。
- 未读笔记要有轻提示。

主文案：
```text
TA 留下了一句话，等你来看
```

主 CTA：
```text
去看看 TA 的笔记
```

### 状态 6：双方完读

用户问题：
```text
我们完成了什么？下一步呢？
```

页面策略：
- 展示完读仪式感。
- 展示共读天数、笔记数、双方进度。
- 引导归档或选下一本。

主文案：
```text
你们一起读完了这本书
```

主 CTA：
```text
收进共读回忆
```

次 CTA：
```text
选下一本
```

### 状态 7：异常/失败

异常态不要使用冷冰冰的通用报错。

推荐文案：
- 网络失败：连接有点慢，稍后再试一下。
- 伙伴已解绑：这段共读关系已经结束，但记录还会保留。
- 对方已有伙伴：TA 已经有共读伙伴了。
- 书籍不可用：这本书暂时还不能共读，换一本试试。

### 状态设计原则

- 每个状态只给一个主行动。
- 空状态必须告诉用户下一步。
- 异常态要解释原因，不只报错。
- 状态文案要体现双人关系。
- 不使用“暂无数据”这类通用文案。
- 首页、结伴页、进度页必须共享同一套状态口径。

## 十六、验收标准与测试清单

后续 UI 改造不能只验收“功能可点”，必须同时验收：

- 状态是否正确。
- 主行动是否唯一。
- 文案是否符合品牌语气。
- 是否体现双人关系。
- 异常时是否给出下一步。
- 是否避免 AI 味和模板化。

### 全局状态验收

未登录：
- 非首页 tab 不闪屏跳转。
- 首页能解释产品价值。
- 不展示共读码、二维码、真实书城完整内容。
- 登录入口清晰。

已登录未绑定：
- 首页主 CTA 是去邀请伙伴。
- 结伴页强展示共读码、二维码、输入框、扫一扫。
- 书城可浏览，但加入共读时引导先绑定。
- 不出现“暂无数据”。

已绑定无书：
- 首页展示伙伴关系。
- 主 CTA 是去主题书房选书。
- 结伴页展示关系状态，不再大面积展示二维码。
- 进度页引导选书。

有书未记录：
- 首页展示当前书。
- 进度页引导记录第一条进度。
- 主 CTA 是记录今天读到哪里。
- 不出现空白笔记列表。

有动态：
- 进度页第一屏展示双方进度。
- TA 最新笔记有轻提示。
- 未解锁笔记不能回复。
- 回复是单层轻互动。

双方完读：
- 展示完读仪式感。
- 展示共读天数、笔记数。
- 有归档/选下一本入口。
- 不只是状态变成 finished。

### 页面验收

首页：
- 是否一眼看出“我和 TA 当前怎样”？
- 是否只有一个主 CTA？
- 是否根据状态切换主文案？
- 是否没有变成功能九宫格？

结伴页：
- 绑定前是否清楚告诉用户如何邀请？
- 绑定后是否明显变成关系展示？
- 绑定后二维码是否弱化？
- 解绑是否低权重展示？
- 复制共读码是否只有一个主要入口？

书城页：
- 是否像主题书房，而不是普通商品列表？
- 分类是否体现心性共修、国学、术数、中医等内容气质？
- 卡片是否展示共读理由？
- 是否避免默认展示不可用书籍？

进度页：
- 第一屏是否展示双方进度？
- 是否突出 TA 的最新动态？
- 笔记流是否像双人日记，而不是评论区？
- 完读时是否有仪式感？

我的页：
- 是否没有抢首页主线？
- 是否更像共读资产管理？
- 目标是否温柔，不像 KPI？
- 历史是否像双人记忆？

### 测试方式

自动化回归：
```text
node scripts/check_frontend_state.js
pytest -q
```

人工状态验收：
```text
未登录
A 登录未绑定
A 绑定 B
A/B 已绑定无书
A/B 有书未记录
A/B 有笔记/回复
A/B 双方完读
解绑后
```

真机验收：
```text
微信登录
手机号授权
扫码绑定
二维码保存相册
订阅消息授权
弱网请求
```

### 产品验收红线

以下情况不通过：
- 出现“暂无数据”作为主要空状态。
- 一个页面同时出现多个同权重主按钮。
- 绑定后仍大面积展示二维码。
- 首页变成功能入口集合。
- 书城默认展示不可加入书籍。
- 文案像营销模板或 AI 文案。
- 异常只显示接口错误。

每次 UI 改版必须附带：
- 改了哪些状态。
- 每个状态的主 CTA。
- 每个状态的空/异常文案。
- 自动化验证结果。
- 人工验收结果。

## 十七、数据指标与产品效果评估

当前阶段指标不以普通 DAU、PV、点击率为核心，而应围绕双人共读关系是否成立。

核心判断：
```text
关系是否建立
共读是否开始
互动是否发生
是否持续
是否完成一本书
```

北极星指标：
```text
有效共读关系数
```

定义：
```text
两人已绑定
且创建了至少一本共读书
且双方都至少记录过一次进度或笔记
```

关键漏斗：
1. 访问首页 -> 登录成功
2. 登录成功 -> 绑定伙伴成功
3. 绑定成功 -> 创建/加入第一本书
4. 有在读书 -> 记录第一条进度/笔记
5. 一方记录 -> 另一方查看/回复
6. 双方有进度 -> 双方完成 -> 归档

第一阶段核心指标：
- 登录成功率
- 绑定成功率
- 绑定后 24 小时内开始共读率
- 有书后首次记录率
- 双方都记录过的共读关系占比
- 平均每本书笔记数
- 7 日共读留存
- 完读率

关系质量指标：
- 双方都有记录的比例
- 双方互相回复的比例
- 平均连续共读天数
- 每本书平均互动次数

早期不应过度关注：
- 总注册用户数
- 首页点击率
- 单次访问时长
- 书城曝光量
- 分享次数
- 商业化转化

基础埋点建议：
```text
login_success
pair_invite_copy
pair_qr_show
pair_bind_success
book_view
book_start_reading
entry_create
entry_reply
entry_read
book_finish
pair_unbind
reminder_save
```

每个事件建议带：
```text
user_id
pair_id
book_id
source_page
created_at
```

第一阶段重点验证：
- 绑定成功率
- 绑定后开始共读率
- 首次记录率

如果 UI 改版只让页面更好看，但上述指标不提升，则不能认为产品体验真正改善。

## 十八、商业化边界

商业化未来会考虑，但当前阶段暂不展开。

当前只做结构预留，不讨论价格、支付、会员权益、课程、付费书单、社群转化等细节。

现阶段优先级：
```text
产品闭环 > 主链体验 > UI 表达 > 真机验证 > 数据指标 > 商业化
```

- 记录进度

- 查看 TA 的笔记
- 回复

## 二十、PRD v1.0 定稿与 UI 改版执行计划

产品讨论阶段到此收束。当前 PRD 可作为 v1.0 执行基线。

定稿主题：
```text
情侣/朋友双人共读陪伴小程序
```

核心闭环：
```text
登录 -> 结伴 -> 选书 -> 共读 -> 记录 -> 回应 -> 完读
```

第一阶段重点：
```text
主链 UI 和状态体验重构
```

### UI 改版执行顺序

1. 全局视觉基建
   - 统一色彩、背景、卡片、按钮、文字、状态文案。
   - 输出全局样式变量和公共样式类。

2. 首页重构
   - 从功能入口页改成“双人共读状态面板”。
   - 覆盖未登录、已登录未绑定、已绑定无书、已绑定有书。

3. 结伴页重构
   - 绑定前工具型。
   - 绑定后关系型。
   - 绑定后弱化二维码，强化关系状态，解绑低权重。

4. 书城页重构
   - 从普通列表改成“主题书房”。
   - 强化分类气质、共读理由、适合关系和阅读节奏。

5. 进度页重构
   - 从记录列表改成“双人共读日记”。
   - 强化双人进度卡、TA 最新动态、单层回复、完读仪式感。

6. 收口验证
   - 自动化回归。
   - 人工状态验收。
   - 真机验收清单。

### 第一阶段不做

- 我的页深度重构。
- 阅读器复杂重构。
- 提醒页复杂重构。
- 历史页复杂重构。
- 商业化。
- 多人小组。
- AI 解读。

### 单页改造交付格式

每改一个页面，必须交付：
- 页面目标。
- 覆盖状态。
- 主 CTA。
- 空状态文案。
- 异常文案。
- 修改文件。
- 验证命令。
- 剩余风险。

### 实施原则

- 一次只改一个主页面。
- 每改完一页就跑验证。
- 不为了视觉牺牲主链清晰度。
- 不把功能从一个页面重复搬到另一个页面。
- UI 必须体现双人关系和内容气质。
- 避免 AI 味和模板化组件。
